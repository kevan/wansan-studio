# SPEC: Data Ingestion Wizard (v1.3)

## 1. 概述与目标
为统一“导入新数据”和“追加数据”的用户体验，我们设计一个统一的、多步骤的**数据接入向导 (Data Ingestion Wizard)**。该向导将取代当前简单的文件选择逻辑，提供更强大、更灵活的数据接入能力，同时解决数据冲突、多 Sheet 导入等核心问题。

**核心目标**:
- **统一体验**: 为所有数据接入场景（新建、追加）提供一致的、可预测的工作流。
- **数据严谨性**: 引入数据预览、类型映射和冲突处理机制，确保数据质量。
- **灵活性与效率**: 支持多 Sheet 导入，并为高频场景提供快捷操作。

---

## 2. 向导触发点
1.  **全局导入 (Full Flow)**: 用户点击主界面的“导入数据”按钮，启动完整流程。
2.  **追加数据 (Append Flow)**: 用户在已存在的表上（例如在 `SchemaEditor` 中）点击“追加数据...”，启动追加流程。

---

## 3. 向导步骤详解

### 第 1 步: 文件与工作表选择 (Sheet Selection)
- **UI**:
  - 用户选择一个或多个 Excel/CSV 文件。
  - **Excel 文件**: 如果文件包含多个工作表 (Sheet)，向导将以列表形式展示所有 Sheet，允许用户勾选一个或多个。
  - **CSV/JSON 文件**: 视为单一数据源，自动进入下一步。
- **逻辑**:
  - **追加流程**: 强制用户只能选择一个 Sheet。
  - **多 Sheet 导入**:
    - **串行配置模式 (默认)**: 内部将用户的选择（例如 `Sheet1`, `Sheet2`）视为多个独立的导入任务。UI 会提示 "正在配置: Sheet1 (1/2)"。
    - **快捷操作 (可选优化)**: 提供一个“将 X 个工作表全部创建为新表”的快捷按钮，允许用户跳过后续的详细配置，直接完成导入。

### 第 2 步: 数据预览与类型确认 (Data Preview & Type Mapping)
- **触发**: 在创建新表时（非追加）。
- **UI**:
  - **数据预览**: 以表格形式展示前 100 行数据。
  - **类型映射**: 每一列的列头都应包含一个下拉菜单，允许用户手动覆盖自动检测的数据类型。
  - **[新增] 唯一键指定 (可选)**:
    - 在每一列的列头旁增加一个**钥匙图标 (🔑)**，点击可将该列指定为“唯一标识符”（即主键）。
    - **UI 提示**: “指定唯一标识字段（如订单ID），有助于后续的数据追加和去重。此步骤可选。”
    - **实时校验**: 当用户指定某列为唯一键时，后台立即对临时表中的数据进行重复值检查 (`GROUP BY ... HAVING COUNT(*) > 1`)。
      - **无重复**: 钥匙图标变为**绿色**，并提示“此列值唯一，可作为主键”。
      - **有重复**: 钥匙图标变为**红色**，并提示“**警告：此列包含重复值**，不能作为唯一主键。”


### 第 3 步: 目标模式选择 (Target Mode Selection)
- **触发**: 仅在**全局导入**流程中。
- **UI**:
  - **[默认选项] 创建新表**: 将当前处理的 Sheet/文件导入为新的数据源。
  - **[可选] 追加到现有表**:
    - 显示一个下拉菜单，列出项目中所有已存在的表。
    - 选择目标表后，系统进行快速的列名匹配度分析，并给出提示（例如“警告：`订单日期` 字段在新数据中不存在，该列将被忽略”）。

### 第 4 步: 唯一键选择 (Unique Key Selection)
- **触发**: 当用户选择“追加数据”模式时。
- **UI**:
  - **引导文本**: “为了防止数据重复，请选择一个能**唯一标识**每一行数据的字段（例如订单ID、用户ID）。”
  - **字段列表**: 列出目标表的所有字段，供用户选择。
  - **智能推荐**: 根据字段名和数据基数，高亮推荐最可能的唯一标识字段。
  - **用户记忆**: 系统可以记住用户对某个表的选择，并在下次追加时默认选中。

### 第 5 步: 冲突处理 (Conflict Resolution)
- **触发**: 后台预检发现唯一键冲突时。
- **UI**:
  - **摘要信息**: 明确告知用户“发现 X 条数据已存在（基于 `唯一标识字段`）”。
  - **决策按钮**:
    - **[A] 保留旧数据 (推荐)**: 仅添加新数据，忽略冲突行。
    - **[B] 使用新数据更新**: 用新文件中的数据覆盖数据库中的旧数据。
    - **[C] 取消**: 中止本次追加操作。

### 第 6 步: 最终确认与执行 (Final Summary & Execution)
- **触发**: 在所有（或所有选中的）Sheet/文件都配置完毕后。
- **UI**:
  - **摘要列表**: 清晰地列出将要执行的所有操作。
    - "✔️ `2024销售数据.xlsx` 将被创建为新表 `t_sales_2024`。"
    - "✔️ `客户回访记录.csv` 将向 `customers` 表追加 450 行新数据。"
    - "⚠️ `12月订单.xlsx` 将向 `orders` 表追加 90 行数据，并**覆盖** 10 行冲突数据。"
  - **执行按钮**: 一个“确认并开始导入”按钮，点击后关闭向导，后台开始处理任务，并在主界面（如侧边栏）显示导入进度。

## 4. 技术实现考量
- **状态管理**: 使用 Zustand 或类似的状态管理器来维护向导的当前步骤、用户选择和各任务的配置。
- **后台任务**: 使用 Electron 的 `ipcRenderer` 和 `ipcMain` 处理长时间运行的文件解析和数据库写入操作，避免阻塞 UI。
- **临时表**: 在进行数据预览和冲突检测时，应将数据加载到 DuckDB 的临时表中，以利用 SQL 的强大能力进行高效分析。
- **组件化**: 向导的每个步骤都应设计为可复用的 React 组件。

通过这个统一的向导，我们将极大地提升数据接入的健壮性和用户体验，为后续的分析功能奠定坚实基础。

## 5. Phase 3: Data Integrity Refactor (Planned)

**背景**: 目前的 `parseFile` 在预览阶段就直接创建了物理表（暂存表），导致 DuckDB 的自动类型推断（Auto-Detection）过早生效。例如，文本类型的 "001" 可能被错误地推断并存储为整数 `1`，且不可逆。

**目标**: 实施 **延迟建表 (Lazy Ingestion)** 策略，确保物理表的创建发生在用户确认类型配置之后。

### 5.1 架构变更
1.  **预览阶段 (Read-Only)**:
    *   **CSV**: 使用 `SELECT * FROM read_csv_auto(...) LIMIT 100` 仅读取数据流，**不创建表**。
    *   **Excel**: 使用流式解析器读取前 100 行用于展示，同样**不创建表**。
    *   **输出**: 返回推断的 Schema 和预览数据给前端。

2.  **执行阶段 (Type-Enforced Write)**:
    *   前端将用户确认的 Schema（列名 + 类型）传回后端。
    *   后端构造带有强制类型的 SQL 语句：
        ```sql
        CREATE TABLE t_final AS 
        SELECT * FROM read_csv_auto('source.csv', types={'code': 'VARCHAR', 'amount': 'DOUBLE'})
        ```
    *   这确保了 "001" 能够按照用户指定的 `VARCHAR` 类型被正确入库。

### 5.2 API 变更
*   **`parseFile`**: 仅返回预览数据，不再产生副作用（不建表）。
*   **`createTableFromSource` (New)**: 替代 `finalizeIngestion`，接收完整的列配置并在入库时强制应用类型。
